Stage 0: lossless single-image PDF acquisition (research only)

Purpose: reuse opaque image source samples when the complete page painting is provably just that image. No image/gold/text/coordinate knowledge enters eligibility. This is acquisition preservation, not OCR correctness, confidence calibration, formal timetable recovery, or production approval.

The prototype requires one unencrypted page, one leaf in one Pages node, origin-zero identical MediaBox/CropBox, Rotate 0, default UserUnit, and image samples exactly equal the integral page width/height (both <=4096). Catalog/Page/Pages/Resources/image/stream dictionaries use closed key whitelists; annotations, groups, optional content, forms, inherited transformations/resources, transparency, masks, decode mappings and unknown entries refuse. This deliberately supports less than all legal image-only PDFs. Unsupported PDF keeps existing Windows renderer fallback unchanged; no production caller is modified.

Before GetPage, dereference the single raw Contents stream and decode with <=4096 content bytes. Its ENTIRE byte stream must tokenize to exactly q, six finite decimal numbers, cm, one unescaped ASCII XObject name, Do, Q. No comments, extra operators, inline images, or ignored compatibility operators are accepted. Typed PdfPig operations must independently be Push, ModifyCurrentTransformationMatrix, InvokeNamedXObject, Pop in that exact order, with the same six numbers/name. Matrix is exactly [sampleWidth,0,0,sampleHeight,0,0]. Image count is one and all four oriented image corners must equal the four page corners. This proves no rotation, reflection, skew, translated partial coverage, crop, or second paint.

A separate bounded raw syntax gate runs BEFORE PdfPig: a single classic xref revision, <=127 sequential unique generation-zero objects, exact xref offsets/startxref/EOF, no object streams, revisions or trailing bytes. All raw dictionary keys are checked for uniqueness after name-escape decoding. Typed bounded literal/hex/array/dictionary walkers preserve context; image/compressed stream bytes are skipped ONLY by direct integral Length and verified endstream boundary, never scanned as names. Relevant PdfPig stream bytes must exactly match a verified raw stream. PdfPig strict mode alone overwrites duplicate keys and is insufficient (preserved stage0 RED). This is a syntax-unambiguity gate; graphics interpretation remains PdfPig plus the complete closed paint contract.

Only DeviceRGB/8-bit/single FlateDecode with no DecodeParms and absent/false Interpolate is supported. Decode uses fixed SharpZipLib 1.4.2 (MIT; research dependency only), requiring authenticated Inflater.IsFinished and RemainingInput=0 as well as exact sample count. Truncated checksums, missing end bytes, concatenated members and trailing junk refuse. Ordinary ZLibStream Read-to-zero was proven insufficient (preserved stage0 RED). Decode is bounded before allocation beyond expected width*height*3; expected exact sample count is mandatory. Raw image stream identity is cross-checked against PdfPig's actual painted image before returning the source RGB, PDF hash, dimensions and typed/raw operation proof. Source RGB is row-major original top-down image data; no resizing, padding, thresholding, pixel masking, clipping, color conversion or glyph splitting occurs. Expected source RGB/hash is checked ONLY by the caller after extraction returns.

Input <=50MiB, raw syntax/comparison shared <=64M charged units, content <=4096 bytes, exact one page/image/content stream, dictionary caps, output <=4096*4096*3 bytes; cancellation before parsing, object checks, bounded block decoding and before return. PdfPig Open itself is synchronous and cannot be interrupted mid-call (existing parser limitation). Source unsupported/limit/cancel outcomes remain distinct; controls are in-memory generated fictional PDFs, never committed binaries. Tests cover known7ceb identity and multicolor row/orientation control, overlay, clipping, rotation/reflection/skew, masks/transparency, annotations, multipage, extra streams/unknown tokens, wrong shape/decode, incomplete/truncated image, limits and cancellation. Production Schema2/Validator5/provider/renderer are untouched; OCR calls zero.
