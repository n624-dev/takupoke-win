# 追加学習v2を既定へ切り替えない理由

別字体の独立した正例cropでは、v2は360→368/384一致、10改善・2退行だった。
しかし実際の復旧用C#経路へ接続すると、同じ単独コード384画像で292→292一致、16改善・16退行となった。
文字編集数は106→123、高信頼度（native 0.8以上）の誤読は24→36へ悪化した。
この結果に基づき、製品の既定は従来のfont-balanced v1を保持する。
日本語の主モデル・製品モデルの取得容量・保存済みモデルを変更しない。

| 同じ2px・384画像 | v1 | v2 |
|---|---:|---:|
| 通常Read経路の完全一致 | 259 | 285 |
| 復旧経路の完全一致 | 292 | 292 |
| 復旧経路の文字編集数／1,871文字 | 106 | 123 |
| 復旧経路のnative 0.8以上の誤読 | 24 | 36 |
| 復旧経路の低スコア画像 | 143 | 81 |
| 復旧経路・通常コード192件の一致 | 190 | 189 |

通常Readの31改善・5退行や、英数字モデル単体の289→297一致を、復旧全体の改善へ置き換えない。
6pxでも復旧の一致は276→276、編集138→140、高スコア誤読22→46だった。余白は2pxを維持する。

これは[先の復旧比較](../ocr-manual-capture-20261016/README.md)と同じ画像を使った接続比較で、
新しい画像・字体・帳票の検証ではない。checkpointはこの比較を見る前に別字体で選択済み。
入力画像の画素は同一で、日本語単体の772観測は文字・confidence・CTC位置が一致し、白4件も空を保った。
worker終了コード0、rawとreaderのSHAを確認してから採点した。追加学習・checkpoint選び直しはしていない。
本番資料での正解率、人の訂正時間は測っていない。iOSは編集していない。
