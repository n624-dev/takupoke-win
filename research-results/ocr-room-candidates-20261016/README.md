# 名称対応表を使った教室コードの訂正候補

現行モデルを変えず、I/l/1・O/0の混同に対して、名称対応表に実在するコードを原画像の横へ表示する。
候補をクリックするとその欄へ入力するが、確認チェックは必ず解除する。同じ候補の再選択でも再確認が必要。
元のOCR・confidence・画像・出典は保持し、利用者の訂正として従来の全体プレビュー・明示採用へ進む。
候補の有無を取得成功や正解の証拠にはしない。

## 固定した新しい文字画像での結果

既に観測した4字体×2サイズ、通常コード192画像・I/l/1/O/0を多く含む難例192画像。
旧2回の比較に使った文字列を除き、seed202610160913で生成した。字体や様式の未見評価ではない。
通常と難例が半数ずつの人工的な集合なので、本番の出現割合や一般正解率を表さない。

認識前に、文字列のSHAによる固定分割で約半数を架空の参照コード表に登録し、残りを未知コードにした。
印字に出現しない架空コード64件も登録した。正解を含む表だけでの候補評価を避け、すべての参照値を入力manifestへ凍結した。
文字列の正解は別ファイルに保存し、workerは原画像とモデル・参照コードのみを読む。
実際のC# `OcrAsciiRefinement`と同じ入力の候補関数を使い、worker正常終了とSHA照合後に採点した。

| 原印字bbox＋2px・384画像 | 件数 |
|---|---:|
| 現行OCRの完全一致 | 275（通常192、難例83） |
| OCRの誤読 | 109 |
| 誤読のうち正解が参照表に登録済み | 65 |
| 誤読のうち正しい候補を提示 | 58（上記65件中） |
| 誤読のうち先頭候補が正解 | 56 |
| 正しかったOCRに別候補を提示 | 15 |
| 参照表に正解のない画像に候補を提示 | 17 |

候補が出たのは82/384画像。76画像に1件、5画像に2件、1画像に3件の候補が出た。
先頭候補をすべて自動採用すると完全一致は275→316になるが、正しかった15件を誤修正する。
製品はこの自動置換を行わない。58件は「訂正を完了した数」や新しいOCR正解数として加算しない。
人の発見率・選択ミス・確認時間は未測定。

同じ384画像の6px条件はOCR264一致、誤読120件中60件で正候補、正しかった12件にも別候補。
余白を広げる変更はしない。2pxと6pxを足して768独立画像とは数えない。
白画像4件は空出力・候補なしだが、損傷・切断検出の資格にはならない。
全3モデルと実際のrouteを含むworkerの最大working setは437,174,272 bytes（約417MiB）。
比較と追加学習を並行したLinux上の実行時間を、Windows文書処理時間には換算しない。

## 適用範囲と確認

ASCIIの数字を含む2〜32文字のコードに限定する。最大2文字のI/l/1・O/0置換だけを照合し、
勝手な大文字化、空白除去、日本語名の類似検索、新しい教室名の生成はしない。
別クラス専用の参照値は使わず、結合欄ではすべての所属クラスが対象の登録だけを使う。
参照規則4096件まで、表示3件まで。順位は相違文字数と文字列順で、正解確率ではない。
名称対応表が未取得・対象外コード・正候補がない場合は、従来の原画像確認と自由入力を使う。

Core300件、Linux Integration1112件が通過。候補の範囲・曖昧性・未知コード・別クラス・上限・中止を確認した。
Windows UIには、選択前の原文保持、候補入力、同じ候補の再選択による確認解除、全体プレビュー、
元OCRと人の訂正の分離、採用前の既存結果保持の操作検証を追加した。Windows結果は実行後に別記する。
UIの成功件数は文字認識の正解率とは別である。
