# テスト保守と検証実行の方針

変更前にテスト一覧から対象コード・機能・既存ケースを検索する。
新しい仕様や既存ケースで検出できない不具合には、入力と期待結果を追加・更新する。
既存テストで十分なら該当ケース、変更を検出できる理由、実行環境と結果を検証記録へ残し、
不要なテスト編集を行わない。期待値の注入や実装に合わせた期待値だけの変更で通さない。
未登録コード・未登録テスト・対応関係と宣言一覧の不整合はCIで拒否する。
検索一覧は対応関係・宣言名・実行方法が変わったときに更新し、本文のハッシュで更新を強制しない。
宣言数、入力パターン数、実行件数、品質合格を区別する。

テストは件数を一律に削減しない。同じ入力・期待結果・経路を重ねる検査を比較し、
固有の不具合を検出するものを保持する。ロジックはネイティブの動作テストを中心にし、
Pythonのソース文字列検査はそこでしか確認できない生成・登録・ライフサイクル契約に絞る。
内部のguard数などに依存する検査は、可能なものから古い画面操作の拒否等の動作検査へ移す。

大きなUIテストは責務と失敗原因が分かる単位へ整理する。
実タップ・入力・遷移・背景復帰・保存・再起動を通す代表シナリオは維持する。
その他の組合せはロジック検査や短い状態別UIへ移す前に、重複と固有の保証を確認する。
対象は実コントロールと観測した表示領域から決める。固定画面座標、結果・許可の注入、
押し直しによる救済、待機切れの成功扱い、検査条件の緩和は行わない。
操作・照会・スクロール・準備・ビルド・開始待ちを区別して計測する。
操作別の根拠なしに時間短縮率を推定しない。

同じジョブでは同じOS・SDK・構成・生成ソースの準備とビルドを再利用する。
build-for-testingとtest-without-buildingを使用し、失敗したビルドを再利用しない。
異なる構成の成果物を共用しない。ジョブ間のキャッシュ・保存用artifactは使用しない。
所有する一時領域とSimulatorを終了・失敗時に回収する。
重いケースを単純に直列化せず、整理後の実測からジョブ数と割り振りを決める。

開発中のPython・Swift検査と関連UI、配布前の包括的検査は段階的に分ける。
OS依存は両OSで検証し、影響範囲不明なら全体を実行する。
配布前には全UI・文字サイズ・VoiceOverを含む必須検証を維持し、
同じコミット・実行ID・試行の成功を公開ゲートで確認する。
軽い開発検証だけで公開しない。mainへのpushによる現行配布経路は、
開発用CIと公開ゲートの設計・検証が終わるまで変更しない。
定期検証とソース加工の縮小は後続の検討とする。

旧開発検証の置換は、利用者が許可した未開始pendingだけを対象にする。
実行中のActionsと公開処理はキャンセルせず、自動cancel-in-progressは有効化しない。

最初の改修対象は、一律テスト編集義務の撤廃、手動訂正UIの整理、
同じジョブ内の準備・ビルド再利用とする。
失敗の調査と修正を並行し、検査を省いて成功として記録しない。
実装・計測の結果はこの方針へ混ぜず、それぞれの検証記録へ残す。
